## Context

The `.github/workflows/scheduled-backup.yml` workflow runs a matrix of backup jobs and then a single `summary` job. The `summary` job currently emits a markdown table header to `$GITHUB_STEP_SUMMARY` but never fills in tenant rows. Matrix job results are available in the `needs` context, but the workflow does not parse them.

The backup data itself is already committed to tenant-specific branches under `backups/`. The summary report should remain lightweight and not duplicate that data.

## Goals / Non-Goals

**Goals:**
- Render a complete per-tenant status table in the GitHub Actions job summary.
- Persist the same report to the repository so it is available after the workflow run expires.
- Keep the change minimal and contained within `scheduled-backup.yml`.

**Non-Goals:**
- Changing the backup format or content in `backups/`.
- Adding external reporting services, notifications, or dashboards.
- Modifying the manual `backup.yml` workflow (it has no summary job).

## Decisions

1. **Use `outputs` on matrix jobs to feed the summary job.**
   - Each `backup` matrix job will expose `tenant`, `status`, and `tag` as job outputs using `echo "<key>=<value>" >> $GITHUB_OUTPUT` in the `Report status` step.
   - The `summary` job will read `needs.backup.outputs` and parse the JSON map with `jq`.
   - *Alternative considered:* Parsing workflow run logs via the GitHub API. Rejected because it requires extra permissions, is slower, and is more fragile than job outputs.

2. **Persist the report to the tenant branch under `reports/`.**
   - The summary job will write `reports/backup-summary-<YYYY-MM-DD>.md` and commit it to the same tenant branch that holds the backup data, keeping tenant-scoped artifacts together.
   - The report path uses the run date so historic reports are retained without overwriting the latest one.
   - *Alternative considered:* A single central `reports` branch. Rejected to avoid cross-branch merge complexity and to preserve tenant isolation.

3. **Keep `$GITHUB_STEP_SUMMARY` as the primary UI view.**
   - The in-Actions report is rendered immediately; the committed file is the durable copy.
   - Both use the same markdown content generated by a shell script.

4. **Status mapping.**
   - `backed-up` → success with tag.
   - `unchanged` → no changes detected.
   - `failed` → backup job failed or `STATUS` was not set.

## Risks / Trade-offs

- [Report commits add noise to tenant branches] -> Mitigation: one small markdown file per day; tags are not created for report-only commits.
- [Matrix job outputs are limited to 1 MB per job] -> Mitigation: report data is tiny (tenant name + status + tag).
- [Summary job runs `if: always()` and must handle missing outputs when a matrix job fails] -> Mitigation: use `fromJSON` with default-empty JSON and iterate safely.

## Migration Plan

1. Merge the workflow change.
2. Trigger the scheduled workflow manually or wait for the next cron run.
3. Verify the `Backup Summary` job shows a populated table and that `reports/backup-summary-<date>.md` appears on the tenant branch.
4. No rollback needed; reverting the workflow file restores the previous behaviour.
