# Dashboard Unhealthy on Backup Failure — Design Session

Raw capture from opsx-propose session 2026-08-14. Triggered by ksb showing **Last: 2026-08-13** and **✅ Healthy** after the Aug 14 scheduled backup failed with `FAILED_EXTERNAL_COMMUNICATION`.

## Context

- Fleet README dashboard is generated by `scripts/generate-readme.mjs` → `generateDashboard()` in `scripts/generate-dashboard.mjs`.
- **Last** column uses the latest restore-point tag date (`ksb/2026-08-13_00-57-38`).
- **State** column uses `formatTenantState()`, which returns `✅ Healthy` whenever `lastBackup !== null` and `objectCount > 0` — it ignores whether the latest backup *attempt* succeeded.
- Scheduled backup matrix already emits per-tenant JSON results (`backup-results/<tenant>.json`) with `status: failed | backed-up | unchanged`.
- Daily markdown reports under `reports/backup-summary-<date>.md` already list per-tenant status including `failed`.
- Summary job generates the report from JSON, then calls `generate-readme.mjs` **without** passing attempt status into the dashboard generator.

## Decision Chain

| Q | Decision |
|---|----------|
| Q1 | **Problem statement:** Operators cannot trust **State** when a tenant's latest scheduled attempt failed but an older restore point still exists. |
| Q2 | **Success criteria:** After a failed scheduled/manual backup attempt, the tenant row shows a non-healthy state until a subsequent attempt succeeds (`backed-up` or `unchanged`). |
| Q3 | **Signal source:** Use the latest backup **attempt status** for the current report day — same data already in matrix JSON and committed summary reports. Do not infer failure from stale **Last** date alone. |
| Q4 | **Healthy outcomes:** `backed-up` and `unchanged` remain **Healthy** (attempt succeeded; tag may or may not advance). |
| Q5 | **Unhealthy outcome:** `failed` → **`⚠️ Backup failed`** (consistent with existing `⚠️ No backups` / `⚠️ Empty backup` pattern). |
| Q6 | **Data plumbing — CI path:** Scheduled summary job passes matrix `backup-results/*.json` into README generation (env var or CLI flag) so dashboard reflects the run that just finished. |
| Q7 | **Data plumbing — local/manual path:** When no in-memory results are supplied, load statuses from the latest `reports/backup-summary-*.md` (reuse `findLatestReport()` in `generate-readme.mjs`). |
| Q8 | **Missing report row:** If tenant has no entry in today's results/report (not in matrix), fall back to current git-only health logic — do not mark failed without evidence. |
| Q9 | **Inactive tenants:** Unchanged — still `❌`; failure status ignored. |
| Q10 | **Scope:** Dashboard State column + spec/tests only. Do not change backup workflow semantics, retry logic, or summary report format. |

## Approaches Considered

### A — Pass matrix JSON into dashboard generator (recommended)

- Summary job sets `BACKUP_RESULTS` (or `--results`) when calling `generate-readme.mjs`.
- `generateDashboard()` accepts optional `attemptStatuses: Map<tenant, status>`.
- Local/manual runs parse latest committed report as fallback.

**Pros:** Accurate, uses existing data, minimal new surface. **Cons:** Requires parsing report table for offline regen.

### B — Infer unhealthy from Last < today after scheduled time

- Mark unhealthy when latest tag date is before today's expected backup window.

**Pros:** No new plumbing. **Cons:** False positives on skipped matrix rows, timezone/cron edge cases, conflates "not run yet" with "failed".

### C — Separate failure column in dashboard

**Pros:** Explicit. **Cons:** Extra column clutter; user asked for State to reflect health.

## Recommendation

**Approach A** — wire attempt status from matrix JSON (CI) and latest report (local). Update `formatTenantState()` and specs/tests.

## Trade-offs Accepted

- Manual README regen without a report file and without `--results` cannot show today's failures (same as today).
- State reflects **latest report day's attempt**, not historical failure if an older report is read locally without refresh.
