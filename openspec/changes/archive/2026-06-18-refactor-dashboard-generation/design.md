## Context

The backup dashboard is generated by `.github/workflows/dashboard.yml`. Today that workflow builds `DASHBOARD.md` using an inline shell script that:

1. Echoes markdown boilerplate.
2. Runs `node scripts/parse-tenants.mjs --all` to list tenants.
3. Re-parses `tenants.yaml` with `grep -A5` to extract `active` and `description`.
4. Runs `git log`, `git ls-tree`, and `git tag` to gather backup metadata.
5. Echoes markdown table rows.

Step 3 is the immediate failure point. `grep -A5 "name: <tenant>"` returns five trailing lines, which can spill into the next tenant block when a tenant entry is short. That produces two matches for `active:` and a newline inside the markdown cell, corrupting the table.

The repository already stores tenant metadata in `tenants.yaml` and relies on a centralized scheduler (ADR-0002). The dashboard is read-only: it consumes the registry and git history and emits a summary. It does not change tenant branches or backup data.

## Goals / Non-Goals

**Goals:**
- Replace the inline shell generation logic with a Node script that is parsed, testable, and deterministic.
- Extract the `tenants.yaml` parser into a shared module so no script re-parses YAML with grep/awk/sed.
- Keep the generated dashboard output identical to the current format, except for fixing the table corruption.
- Make the core generation logic unit-testable without a real git repository.
- Convert `scripts/backup-stats.sh` to a Node script for consistency.

**Non-Goals:**
- Changing the dashboard layout, columns, or styling.
- Adding new dashboard sections (e.g., charts, history graphs).
- Changing the branch-per-tenant model or backup schedule.
- Adding new dependencies (use Node built-ins only).

## Decisions

### 1. Extract `loadRegistry()` to `scripts/tenant-registry.mjs`

**Rationale:** Two scripts need to read `tenants.yaml`: `parse-tenants.mjs` and the new `generate-dashboard.mjs`. A shared module removes duplication and prevents divergent parsing logic.

**Alternative considered:** Keep `loadRegistry()` inside `parse-tenants.mjs` and import from there. Rejected because `parse-tenants.mjs` is a CLI entry point with immediate side effects; importing it as a library is confusing and couples consumers to its CLI behavior.

### 2. Generate dashboard from a single Node script writing to stdout

**Rationale:** Matches the existing pattern (`parse-tenants.mjs` writes JSON to stdout) and makes the workflow step a single line: `node scripts/generate-dashboard.mjs > DASHBOARD.md`. Stdout is composable and easy to inspect in tests.

**Alternative considered:** `--output <file>` flag. Rejected because stdout is simpler and aligns with the user's explicit preference.

### 3. Separate git-facing shell commands into thin wrapper functions

**Rationale:** `generate-dashboard.mjs` needs `git log`, `git ls-tree`, and `git tag`. Wrapping each call in a small function keeps the core table-generation logic pure and easy to test with injected data.

**Alternative considered:** Use a Node git library such as `simple-git`. Rejected to avoid adding dependencies.

### 4. Keep `backup-stats.sh` logic but move it to `generate-backup-stats.mjs`

**Rationale:** The shell script uses `du`, `find`, and `git status --porcelain`. A Node equivalent using `fs`, `child_process`, and `git` is straightforward and removes another shell script from the repository.

**Alternative considered:** Leave `backup-stats.sh` untouched. Rejected because the user explicitly asked to include it in the refactor.

## Risks / Trade-offs

| Risk | Mitigation |
|------|------------|
| `tenant-registry.mjs` changes break `parse-tenants.mjs` matrix output | Preserve the existing CLI contract exactly; run `test-parse-tenants.mjs` after refactor |
| `git ls-tree` behavior differs between local environment and GitHub Actions | Use the same ref format (`origin/<tenant>`) and fallback to local branch; test in both contexts |
| Object count differs from current shell logic | Port the exact filter (`\.json$`) and path (`backups/<tenant>/`) |
| Markdown table still breaks if a description contains `\|` | Escape `\|` characters in description values in the Node script |

## Migration Plan

1. Create `scripts/tenant-registry.mjs` by extracting `loadRegistry()` from `parse-tenants.mjs`.
2. Update `scripts/parse-tenants.mjs` to import `loadRegistry()` from the new module and verify CLI output is unchanged.
3. Create `scripts/generate-dashboard.mjs` with exported core functions and a CLI entry point.
4. Create `scripts/generate-backup-stats.mjs` as a Node replacement for `scripts/backup-stats.sh`.
5. Update `.github/workflows/dashboard.yml` to call `node scripts/generate-dashboard.mjs > DASHBOARD.md`.
6. Delete `scripts/backup-stats.sh` after confirming `generate-backup-stats.mjs` is wired in.
7. Add `scripts/test-generate-dashboard.mjs` to exercise the core table builder.
8. Run the dashboard workflow manually to verify the table renders correctly.

Rollback: restore the previous version of `.github/workflows/dashboard.yml` and the deleted `scripts/backup-stats.sh` from git history.

## Open Questions

- Should `generate-backup-stats.mjs` continue to be invoked only by external callers, or should `dashboard.yml` call it and embed stats into the dashboard? Currently `backup-stats.sh` is not referenced by `dashboard.yml`; the proposal leaves that behavior unchanged.
- Should `tenant-registry.mjs` also export cron helpers (`matchesCron`, `previousCronTime`) so other scripts can reuse them? Out of scope for this change, but the shared module makes that future refactor trivial.
